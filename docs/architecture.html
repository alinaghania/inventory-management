System architecture

Three layers, one direction of travel. The browser owns all rendering and view state; the server owns all filtering and validation; the data layer is read-only and loaded exactly once at process start.

Data flow

One round trip, traced end to end — a user changing the warehouse filter on the dashboard. Filtering is server-side; the client sends criteria, never predicates.

01
FilterBar.vue
User selects a warehouse. v-model writes to selectedLocation, a ref that lives at module scope in the composable — so every component sharing it updates at once.
02
useFilters.js
getCurrentFilters() assembles the four filters into a plain object, renaming selectedLocation to warehouse and selectedPeriod to month to match the API contract.
03
views/Dashboard.vue
A watcher on the filter refs re-invokes the loader. Loading and error refs are set around the call; the template renders all three states.
04
api.js
Builds URLSearchParams, appending only values that are not 'all' — the sentinel never reaches the wire. Issues the axios GET.
05
main.py — route
FastAPI coerces query params into Optional[str] arguments. The route calls apply_filters(), then filter_by_month() where a time dimension exists.
06
main.py — filters
Each helper rebinds a new list rather than mutating in place, so the module-level fixtures survive the request intact. Quarters expand to three month prefixes before matching.
07
Pydantic
Routes declaring response_model validate and serialise every record. Aggregate routes return bare dicts and skip this step entirely.
08
views/*.vue
The response lands in a raw ref. Derived figures — totals, low-stock counts, chart geometry — are computed, so they recalculate only when the raw ref changes.

Observations

Found while reading the source for this document. The security notes are expected for a local demo and are documented as such in server/CLAUDE.md; the first three are genuine inconsistencies.

Resolved

The /api/tasks contract is now complete

An earlier read of this codebase found App.vue calling four /api/tasks endpoints that had no server routes. All four now exist in main.py — GET, POST, PATCH and DELETE — and are covered by 21 tests in tests/backend/test_tasks.py.

Dead code

Purchase-order client methods have no route and no caller

createPurchaseOrder and getPurchaseOrderByBacklogItem exist in api.js, are never called by any component, and have no server counterpart. The PurchaseOrder and CreatePurchaseOrderRequest models are likewise defined but unused.

Orphan

Backlog.vue is unreachable

A complete 152-line view that is never imported in main.js and has no route or nav entry. /api/backlog is live and returns data, so the backlog feature is server-complete but has no way in from the UI.

Data gap

purchase_orders.json is an empty array

/api/backlog computes has_purchase_order by scanning that list, so the flag is unconditionally false for all four backlog items. The join works; there is simply nothing to join against.

By design

No auth, wildcard CORS, no persistence

allow_origins=["*"], no authentication, and no rate limiting. Mutations would not survive a restart in any case, since fixtures reload from disk at import. Called out explicitly as local-development-only in the server guide.

Scaling note

Every aggregate is recomputed per request

/api/reports/quarterly and /api/reports/monthly-trends walk all 250 orders on each call, with no caching or indexing. Fine at this size; the first thing to revisit behind a real database.
